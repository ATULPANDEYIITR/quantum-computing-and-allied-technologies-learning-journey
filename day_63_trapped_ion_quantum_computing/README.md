# Trapped-Ion Quantum Computing: Ion Traps and Laser Control

## Scope

This repository models the control layer of a small trapped-ion quantum computer. The central physical abstraction is a chain of trapped ions whose internal electronic states provide qubits. Laser pulses provide controlled interactions with those qubits, while the ions' collective motion supplies an interaction channel for two-qubit gates.

The five implementations use the same physical domain but deliberately emphasize different engineering perspectives:

| File | Primary perspective | Main implementation |
|---|---|---|
| Python | State-vector simulation and control workflow | Qubit register, laser pulses, rotations, entangling interaction, measurement |
| JavaScript | Event-driven control | Laser channels, pulse events, scheduling, policy evaluation |
| C++17 | Control-engineering case study | Typed trap model, calibration, pulse scheduling, safety validation |
| Java 17 | Enterprise domain model | Records, interfaces, services, policies, immutable collections, explicit validation |
| PostgreSQL | Persistent experimental-control model | Trap inventory, ions, laser channels, calibration, pulses, checks, approvals, reporting |

The implementations are educational control-system models. They are not replacements for a laboratory's electromagnetic simulation, optical design software, pulse-shaping stack, real-time controller, or experimentally validated quantum-device model.

## Physical Model

A trapped-ion processor confines charged atomic ions in an electromagnetic potential. A linear arrangement is represented here by separate radial and axial trap frequencies.

The simplified relationship used by the implementations is:

`radial frequency > axial frequency`

This represents a regime in which the model treats the ions as a linear chain with distinguishable collective motional modes.

Each ion has:

- an identifier
- a mass
- an axial frequency
- a logical position
- an operational status in the database model

The qubit is encoded in two selected internal states of an ion. The source code uses `0` and `1` as the computational basis without assuming a particular atomic species or hyperfine-state implementation.

## Laser Control

Laser control is represented by pulse parameters rather than raw optical waveforms.

A pulse contains:

| Parameter | Meaning |
|---|---|
| Duration | Time for which the control interaction is applied |
| Rabi frequency | Effective coupling strength between the laser and the internal qubit transition |
| Detuning | Frequency offset from the selected transition or control condition |
| Phase | Optical/control phase used by the effective gate model |
| Ion | Primary addressed ion |
| Target ion | Second ion for an entangling operation |
| Gate type | Single-qubit or entangling operation |

The effective Rabi frequency is modified by a calibration scale. The effective detuning includes a measured frequency offset.

The implementations reject pulses when the effective detuning exceeds the configured safety threshold, when duration is excessive, or when estimated optical power exceeds the channel limit.

## Single-Qubit Control

A resonant laser interaction can rotate an ion's internal state on the Bloch sphere. The Python implementation explicitly constructs a two-by-two unitary matrix from the effective Rabi coupling, detuning, phase, and pulse duration.

The state transformation is applied to the relevant qubit of a full state vector.

For a two-level subsystem, the model uses a generalized rotation generated by a combination of transverse coupling and detuning. The detuning contribution changes the effective rotation axis rather than simply changing the pulse duration.

This provides a useful distinction between:

- pulse duration
- Rabi frequency
- detuning
- optical phase

They are independent control parameters and are not interchangeable.

## Two-Qubit Control

The implementations model an entangling operation as an effective interaction between two ions.

The Python implementation applies an idealized operator of the form:

`exp(-i * theta * X⊗X / 2)`

where `theta` is derived from the calibrated pulse area.

The C++, JavaScript, Java, and PostgreSQL implementations focus on whether such a pulse is valid rather than attempting to reproduce the complete time-dependent ion-motion Hamiltonian.

This distinction is important. A laboratory entangling gate depends on details such as:

- collective motional modes
- laser frequency components
- bichromatic detuning
- optical phase
- Lamb-Dicke coupling
- motional occupation
- pulse envelope
- spontaneous emission
- laser intensity fluctuations
- frequency drift
- mode-frequency drift

The repository models the control-policy layer around these quantities rather than claiming to reproduce all of the underlying physics.

## Motional Modes

The trap model exposes a simplified mode-separation quantity:

`mode spacing = radial frequency - axial frequency`

The value is used as a control-policy prerequisite for entangling operations.

This is a deliberately conservative abstraction. Actual trapped-ion systems have multiple collective normal modes, and an entangling gate normally addresses selected modes through carefully calibrated laser frequencies and pulse shapes.

The model therefore treats mode separation as an eligibility condition rather than as a complete physical description.

## Calibration

Calibration is a separate concern from pulse execution.

A laser channel stores:

- maximum permitted optical power
- Rabi-frequency scale
- frequency offset
- active status

A calibration record stores:

- measured Rabi frequency
- measured detuning
- tolerance
- calibration status
- measurement time
- expiration time

A pulse can require a current passed calibration.

This prevents a control request from being treated as safe merely because its nominal parameters are valid. The measured control channel must also be within its calibration lifetime.

## Python Implementation

The Python program provides the most direct state-vector view of the domain.

### Main components

`Ion` represents a physical ion.

`TrapConfiguration` represents the principal trap and laser constraints.

`LaserPulse` represents an individual control operation.

`QubitRegister` stores a normalized complex state vector.

`LaserController` converts validated pulse parameters into effective quantum operations.

`PulseScheduler` prevents overlapping pulses that address the same ion.

`TrapProcessor` coordinates the control components and performs repeated measurement.

### State representation

For `n` qubits, the register contains `2^n` complex amplitudes.

The basis states are represented by integer indices. A two-qubit state therefore has four amplitudes:

- `|00>`
- `|01>`
- `|10>`
- `|11>`

The implementation normalizes the state after each operation and verifies that the total probability remains approximately one.

### Measurement

Measurement samples the probability distribution defined by the squared magnitudes of the amplitudes.

After measurement, the register collapses to the sampled computational basis state.

Repeated shots produce a histogram, allowing the program to show the statistical character of quantum measurement.

### Validation

The Python implementation rejects:

- unknown ions
- invalid trap frequencies
- non-positive pulse durations
- invalid Rabi frequencies
- excessive detuning
- missing entangling targets
- conflicting scheduled pulses
- invalid measurement-shot counts

Assertions at the end verify core simulator invariants.

## JavaScript Implementation

The JavaScript program uses an event-driven control architecture rather than mechanically reproducing the Python state-vector operations.

### Event model

`IonTrapController` extends `EventEmitter`.

Two useful events are emitted:

- `pulseScheduled`
- `controlApplied`

This separates control requests from observers that may record, display, audit, or monitor them.

`PulseScheduler` also emits a scheduling event after a pulse passes its overlap checks.

### Laser channels

A `LaserChannel` owns calibration state and converts nominal Rabi frequency into effective Rabi frequency.

This reflects a useful software boundary: callers request a control parameter, while the channel applies its current calibration.

### Policy evaluation

`ControlPolicy` validates:

- effective detuning
- pulse duration
- optical-power estimate
- target-ion requirements
- trap-mode separation

The policy is kept separate from `IonTrapController`, allowing the control service to enforce rules without embedding every rule in event-processing code.

### Measurement

The JavaScript measurement service validates the supplied probability distribution and shot count.

The sample source uses Node.js cryptographic randomness rather than an application-level predictable pseudo-random generator. This does not make the simulated quantum process physically random; it simply avoids introducing deterministic application randomness into the measurement demonstration.

## C++17 Implementation

The C++ implementation treats the system as a compact control-engineering case study.

### Domain structures

The program defines:

- `Ion`
- `Trap`
- `LaserChannel`
- `Pulse`
- `CalibrationResult`

Enums distinguish pulse types and calibration results.

### Calibration service

`LaserCalibration` evaluates a measured Rabi frequency against a target and checks measured detuning against a limit.

A five-percent relative Rabi-frequency tolerance is used in the executable example.

Calibration failure prevents the control workflow from proceeding.

### Scheduler

`PulseScheduler` stores pulses in chronological order.

For each new pulse it computes the set of ions occupied by the operation. An operation is rejected if its time interval overlaps another operation that uses any of the same ions.

This permits parallel operations on independent ions while preventing conflicting operations on the same physical resources.

### Performance

The scheduler uses a vector and performs a linear conflict scan.

For a small experimental pulse sequence this is straightforward and has low implementation complexity. A large real-time system could use interval indexes, resource-specific queues, or a specialized timing data structure.

The state-vector representation is intentionally absent from this implementation. C++ instead concentrates on the resource-management and validation layer.

## Java 17 Implementation

The Java implementation models trapped-ion control as an enterprise domain service.

### Domain records

Java records provide immutable representations of:

- `Ion`
- `Trap`
- `LaserCalibration`
- `LaserChannel`
- `Pulse`

This prevents accidental mutation of critical control parameters after domain objects have been constructed.

### Policy interface

`ControlPolicy` defines the validation boundary.

`ConservativeLaserPolicy` implements the rule set for:

- detuning
- duration
- optical power
- entangling-gate mode separation

The policy can therefore be tested independently from the service that schedules pulses.

### Service boundary

`IonTrapService` owns:

- ion lookup
- laser-channel lookup
- policy evaluation
- pulse scheduling

The service does not directly implement every physical equation. Instead, it coordinates domain objects and applies explicit policies.

### Calibration service

`CalibrationService` produces an immutable result containing:

- status
- measured Rabi frequency
- measured detuning

The result is then used as a gate for the subsequent control workflow.

### Collections

The implementation uses:

- `Map` for ion and laser lookup
- `Set` for physical-resource conflict detection
- immutable `List` snapshots for scheduled pulses
- streams for pulse-type aggregation

This makes the domain boundaries explicit and reduces accidental state changes.

## PostgreSQL Model

The PostgreSQL implementation persists the experimental-control domain.

The schema is named `trapped_ion_control`.

### Core relationships

The relational structure is:

→ `ion`

`trap_system`
→ `laser_channel`
→ `calibration`

`trap_system`
→ `control_policy`

`trap_system`
→ `experiment`
→ `pulse_sequence`
→ `pulse`

`pulse_sequence`
→ `control_check`

`pulse_sequence`
→ `pulse_approval`

`experiment`
→ `measurement_run`
→ `measurement_result`

This separates physical hardware, control configuration, experimental workflows, validation, approvals, and observations.

## Database Constraints

The schema uses database-level constraints rather than relying entirely on application code.

Examples include:

- radial frequency must exceed axial frequency
- laser wavelength must be within the configured model range
- masses and frequencies must be positive
- entangling pulses must have a distinct target ion
- measurement counts cannot be negative
- calibration expiry must follow calibration measurement time
- measurement shots have an explicit upper bound

These constraints protect the stored domain even when data enters through a different application.

## Pulse Validation Trigger

`validate_pulse_policy()` checks a new pulse against:

- the primary ion's trap
- target-ion membership
- trap control policy
- active laser channel
- effective detuning
- pulse duration
- estimated optical power
- current calibration

The validation occurs before insertion or update.

This is important because a pulse is not considered valid solely because its raw values look reasonable. The values must be valid in the context of the hardware configuration and current calibration.

## Pulse Conflict Trigger

`reject_overlapping_pulse()` searches the same sequence for temporal overlap.

Two pulses conflict when:

- their time intervals overlap
- and they share a primary or target ion

Operations on independent ions can therefore overlap.

This represents a resource scheduling rule rather than a quantum-mechanical law.

## Control Checks

A sequence can have explicit checks for:

- laser calibration
- motional-mode separation
- timing conflicts
- power and detuning limits

A check has a status of:

- `pending`
- `passed`
- `failed`

The sequence eligibility view requires all recorded checks to pass.

## Approval Model

The database distinguishes technical checks from human approval.

A `control_check` records an automated or procedural control condition.

A `pulse_approval` records a decision by an operator.

The distinction is intentional:

`control checks` → evidence that technical conditions are satisfied

`approvals` → explicit authorization decision

The eligibility view requires both classes of condition.

## Measurement Model

A measurement run records the number of shots.

Individual result rows record a bitstring and its count.

For the sample experiment, the database contains four computational outcomes:

| State | Sample count |
|---|---:|
| `00` | 248 |
| `11` | 241 |
| `01` | 6 |
| `10` | 5 |

The total is 500 shots.

The reporting query computes the percentage of outcomes in the correlated `00` or `11` set. This is a simple diagnostic and should not be interpreted as a complete fidelity estimate for a physical Bell-state experiment.

## Failure Conditions

The implementations intentionally reject unsafe or inconsistent states.

Examples include:

| Failure | Control response |
|---|---|
| Unknown ion | Reject operation |
| Missing entangling target | Reject operation |
| Same ion used as both entangling endpoints | Reject operation |
| Excessive detuning | Reject operation |
| Excessive pulse duration | Reject operation |
| Excessive estimated optical power | Reject operation |
| Missing current calibration | Reject operation |
| Overlapping pulses on the same ion | Reject scheduling request |
| Invalid trap frequency relationship | Reject trap configuration |
| Invalid measurement distribution | Reject measurement |
| Failed calibration | Block control workflow |

These checks illustrate why experimental control software needs explicit validation instead of treating a pulse as an unconstrained function call.

## Security and Operational Controls

A physical-control application has a different security boundary from an ordinary data-processing application.

The implementations therefore model several relevant controls:

- bounded pulse duration
- bounded detuning
- bounded optical power
- explicit calibration status
- active/inactive laser channels
- resource-conflict prevention
- explicit operator approval
- database-level integrity constraints
- transactional updates

In a production system, these controls would normally be supplemented by authenticated operator identities, authorization policies, immutable audit records, hardware interlocks, independent safety systems, signed configuration changes, network isolation, and real-time watchdog mechanisms.

The sample programs do not claim to provide those laboratory safety functions.

## Performance Considerations

The Python state-vector simulator scales exponentially with the number of qubits because a state vector requires `2^n` amplitudes.

For `n` qubits:

- state storage is `O(2^n)`
- a single-qubit state-vector update is `O(2^n)`
- the two-qubit effective operation is also `O(2^n)`

This makes the Python implementation appropriate for small demonstrations rather than large quantum processors.

The scheduling implementations use linear scans over scheduled pulses. This is practical for small pulse sequences. Larger systems would normally use resource-aware interval scheduling or specialized real-time control infrastructure.

PostgreSQL indexes are placed on fields used by recurring joins, status queries, timing retrieval, and calibration-expiration lookups. The schema does not index every column because unnecessary indexes increase write cost and storage consumption.

## Important Physical Limitations

The control models simplify several experimental effects.

They do not fully simulate:

- Coulomb-coupled normal-mode spectra
- Lamb-Dicke parameters
- thermal motional occupation distributions
- spontaneous-emission dynamics
- off-resonant scattering
- laser phase noise
- laser intensity noise
- magnetic-field noise
- microwave coupling
- optical aberrations
- pulse-envelope optimization
- full master-equation dynamics
- leakage outside the computational subspace
- experimentally measured gate fidelity

The effective entangling operator is therefore a software abstraction for the outcome of calibrated laser-mediated interaction, not a replacement for a physical Hamiltonian simulation.

## Relationship Between the Implementations

The five source files deliberately divide responsibilities.

Python answers:

`How does a small state-vector model respond to calibrated laser operations?`

JavaScript answers:

`How can laser-control requests be represented as events and validated through an asynchronous control architecture?`

C++ answers:

`How can a compact control engine validate hardware resources, calibration, timing, and pulse safety efficiently?`

Java answers:

`How can the same domain be represented with explicit enterprise types, policies, services, and immutable state?`

PostgreSQL answers:

`How can physical configuration, calibration, pulse workflows, approvals, checks, and measurements be stored with database-level integrity?`

The common domain is trapped-ion control, but the implementations are not line-for-line translations of one another.

## Design Distinctions

The domain contains several concepts that should not be collapsed into one object.

| Concept | Meaning |
|---|---|
| Trap | Physical confinement environment |
| Ion | Physical qubit carrier |
| Laser channel | Optical control resource |
| Calibration | Measured state of a control resource |
| Pulse | Requested physical control action |
| Pulse sequence | Ordered collection of control actions |
| Control check | Technical eligibility condition |
| Approval | Explicit authorization decision |
| Measurement run | Collection of experimental shots |
| Measurement result | Observed outcome distribution |

This separation allows a pulse to be technically valid while a sequence is still blocked by an approval requirement or a failed control check.

## Educational Focus

The artifacts connect quantum-computing concepts to concrete software engineering concerns:

- physical resource modeling
- calibrated control parameters
- state representation
- unitary operations
- entangling interactions
- pulse scheduling
- validation
- event-driven processing
- typed domain modeling
- database integrity
- transactional workflow
- measurement statistics
- operational failure handling

The central design principle is that a quantum-control operation is not merely a mathematical gate. In an operational system, the gate must also be associated with a physical ion, a calibrated control channel, a valid time window, permitted control parameters, and a valid experimental workflow.
